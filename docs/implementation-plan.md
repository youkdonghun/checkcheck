# 체크체크 구현 설계 초안

작성일: 2026-09-10

이 문서는 개발 전에 작성한 설계안이다. 이후 0.1 버전에서 Windows 실행 파일, 기본 규칙, 바른 API 선택 연동, 로컬 AI 선택 설치, 검토 화면, 전역 입력 제어를 구현했다. 현재 지원 범위와 실제 검증 상태는 루트 README.md와 사용안내.txt를 따른다. 실제 한글·Word 직접 연동은 후속 항목이다.

## 1. 제품 동작

글을 쓰던 입력칸에서 단축키를 누르면 선택한 글을 가져온다. 선택한 글이 없을 때에는 식별 가능한 현재 입력칸 전체를 대상으로 한다. 가져오지 못하면 직접 붙여넣기 화면을 제공한다.

검사 모드와 검토 보기는 별개의 설정이다.

| 검사 모드 | 목표 | 기본 제안 단위 |
| --- | --- | --- |
| 최소 교정 | 맞춤법·띄어쓰기·오탈자·문법을 고치고 말투 유지 | 단어·구절 |
| 자연스럽게 | 의미와 기존 말투를 유지하며 어색한 표현 정리 | 문장 |
| 업무용 | 사실을 유지하면서 명확하고 정중한 업무 표현으로 변경 | 문장 |

한국어·영어·혼용 문장을 대상으로 한다. 업무용 기본 어조는 과도한 존칭을 피한 정중한 표현으로 한다. 날짜·금액·수량·이름·URL·코드·부정 표현·기한을 보존하고, 원문에 없는 약속·사과·이유를 덧붙이지 않는 것을 평가 기준으로 삼는다. 이러한 지침을 모델에 전달하는 것만으로 보존이 보장되지는 않으므로 별도 검증을 수행한다.

## 2. 비교와 순차 검토

두 보기는 하나의 교정 세션과 제안별 선택 상태를 공유한다. 보기를 바꿔도 이미 검토한 결과가 사라지지 않는다.

- **전후 비교:** 고정된 원문과 수정안을 나란히 표시한다. 좁은 창에서는 위아래로 배치한다. 삽입·삭제·띄어쓰기 변경을 색과 기호로 구분한다.
- **하나씩 검토:** 현재 위치와 전체 건수, 해당 문맥, 수정 전·후, 이유를 보여준다. 바꾸기·넘기기·이전·되돌리기를 제공한다.
- **수정안 미리보기와 확정 결과:** 아직 검토하지 않은 제안이 포함된 화면에는 ‘미리보기’를 표시한다. 원래 입력칸에 반영되는 결과는 사용자가 선택한 제안으로만 만든다. 전체 적용은 남은 제안을 명시적으로 선택하는 동작으로 처리한다.
- **문장 다듬기:** 문장 전체를 하나의 적용 단위로 취급한다. 화면에서 단어별 차이를 보여주더라도 문장 재작성 결과의 일부 조각만 독립적으로 승인하지 않는다.
- **검토 중 변경:** 사용자가 초안을 직접 수정하거나 검사 모드를 변경하면 현재 초안 기준으로 다시 분석하고 오래된 미검토 제안을 폐기한다. 처음 가져온 원문과 이전 작업 기록은 유지한다.

## 3. 원래 앱에서 교정하는 수준

‘한글의 맞춤법 검사처럼 하나씩 검토’하는 UX와 ‘실제 한글 앱에 직접 연결’하는 기능은 별도로 구현한다.

| 수준 | 제공 동작 | 적용 조건 |
| --- | --- | --- |
| 검토 창 | 체크체크 안에서 전후 비교·개별 승인 후 결과 복사 | 텍스트를 가져올 수 있음 |
| 선택 영역 반영 | 검토한 결과를 원래 선택 영역에 한 번 반영 | 대상·범위를 다시 확인하고 정확히 교체 가능 |
| 원문에서 하나씩 교정 | 원래 앱의 해당 위치 선택 → 해당 오류만 교체 → 다음 오류 | 앱에서 범위 지정·부분 교체·변경 후 검증 가능 |

첫 버전은 검토 창과 검증된 일반 텍스트 입력칸의 선택 영역 반영까지 구현한다. 원문에서 하나씩 교정하는 기능은 지원 앱별로 추가한다. 지원 여부가 확인되지 않은 앱은 결과 복사를 제공한다.

문서 위의 밑줄 오버레이는 후속 기능이다. 스크롤·확대율·줄바꿈·다중 모니터 배율을 추적해야 하므로 첫 직접 연동에서는 앱 자체의 선택 표시를 우선 이용한다.

## 4. 모듈 구성

Windows 우선 구현 후보는 C#/.NET + WPF다. UI와 교정 로직, OS 연동을 분리해 이후 다른 화면 기술이나 플랫폼으로 옮길 수 있게 한다. WPF 자체는 Windows 전용이다.

| 모듈 | 책임 |
| --- | --- |
| Desktop UI | 트레이, 단축키 설정, 검토 창, 진행 표시, 취소 |
| Capture / Target Adapter | 원래 창·입력칸 식별, 선택 범위 읽기·선택·교체, 지원 기능 보고 |
| Review Session | 원문 스냅샷, 현재 초안, 모드, 제안 상태, 되돌리기 기록 |
| Proofreading Provider | 검사 요청과 문장별 수정 후보·수정 이유 반환 |
| Diff / Validation | 로컬에서 변경 위치 계산, 원문 일치 확인, 보호 표현 검사, 충돌 처리 |
| Apply Coordinator | 대상 재확인, 변경 반영, 반영 결과 검증, 실패 상태 처리 |

Adapter는 앱 이름만으로 성공을 가정하지 않는다. 실제 입력 요소별로 읽기, 범위 재선택, 부분 교체, 서식 보존, 되돌리기 가능 여부를 보고한다. 클립보드는 텍스트 이동 수단이며 위치를 식별하는 수단으로 사용하지 않는다.

## 5. 제안과 원문 위치 관리

세션에는 다음 정보가 필요하다.

- 세션 ID와 원문 버전, 변경되지 않는 원문 스냅샷
- 대상 프로세스·창·입력 요소, 제공되는 경우 문서·범위 식별자
- 선택 범위와 앞뒤 문맥, 현재 초안 버전
- 제안 ID, 문장 ID, 검사 모드, 원문 조각, 대체문, 이유
- 제안별 상태: 미검토 / 선택 / 건너뜀 / 오래됨
- 초안 변경 기록과 외부 반영 기록을 구분한 기록

모델에게는 문장 ID와 원문을 제공하고 수정문을 받는다. 모델이 반환한 문자 위치를 그대로 신뢰하지 않고, 프로그램이 원문과 수정문을 비교해 변경 범위를 계산한다. 반복되는 동일 단어는 문자열 검색 결과 첫 번째에 무조건 적용하지 않는다.

내부 텍스트 위치 단위는 UTF-16으로 통일하되, 화면에서 표시하는 문자 경계는 한글 자모·결합 문자·이모지 묶음을 고려한다. 문서 API의 위치 단위와 내부 위치를 변환하는 책임은 Adapter에 둔다. 줄바꿈이나 유니코드 정규화가 필요한 경우 원문 위치로 돌아갈 수 있는 매핑을 유지한다.

겹치는 제안은 동시에 적용하지 않는다. 같은 문장의 재작성과 그 안의 단어 교정은 대안 또는 하나의 제안 묶음으로 처리한다. 문장 재작성을 선택하면 해당 문장의 다른 제안은 폐기하고 필요하면 다시 검사한다.

고정된 텍스트 스냅샷의 겹치지 않는 변경은 뒤에서 앞으로 적용할 수 있다. 외부 문서의 순차 교정은 매번 최신 범위를 다시 확인하고 변경 후 재탐색한다. 이전 문자 위치에 길이 차이만 더해 계속 쓰는 방식으로 모든 앱을 처리하지 않는다.

## 6. 외부 반영 절차

1. 검사 호출 시 체크체크가 포커스를 가져오기 전에 원래 대상과 선택 범위를 기록한다.
2. 입력 요소가 편집 가능한지, 선택 범위가 유효한지 확인한다. 비밀번호 입력칸은 제외한다.
3. 검토는 메모리의 초안에서 진행한다. 원래 앱에는 사용자가 반영을 선택할 때 쓴다.
4. 쓰기 직전에 대상과 범위를 다시 찾고, 현재 텍스트가 예상한 원문과 일치하는지 확인한다.
5. 사용자가 원문을 바꾸었거나 위치가 불명확하면 반영하지 않고 다시 가져오도록 한다.
6. 교체 후 실제 결과를 다시 읽어 확인한다. 확인할 수 없으면 성공으로 표시하지 않는다.
7. 재시도할 때 이미 반영된 변경을 중복 삽입하지 않도록 반영 기록과 현재 결과를 확인한다.

원문에서 하나씩 교정하는 모드에서는 사용자가 누른 ‘바꾸기’마다 위 절차를 실행하고, 변경된 원문을 다음 작업의 기준으로 갱신한다. 다른 창에 포커스가 간 경우 대상 재확인 없이 키 입력을 보내지 않는다.

한글 IME 조합 중에는 Enter를 보내 확정하지 않는다. 메시지 전송 등 부작용 없이 조합 완료를 감지하거나 잠시 대기 후 재시도하도록 구현 가능성을 확인한다.

기존 클립보드는 지원 형식 범위에서 보존한다. 작업 도중 사용자가 새 내용을 복사했으면 이전 클립보드를 덮어씌워 복구하지 않는다. 클립보드 전체 형식과 원래 커서 위치의 완전 복원은 앱별로 검증하기 전에는 보장하지 않는다.

검토 창 안의 되돌리기는 자체 변경 기록으로 제공한다. 외부 문서의 되돌리기는 앱의 트랜잭션·Undo 지원에 맞추어 구현하고 검증한다. 서식 문서를 일반 텍스트 백업으로 복구할 수 있다고 가정하지 않는다. 취소하더라도 이미 외부에 반영된 변경이 자동으로 되돌아간다고 표시하지 않는다.

## 7. 문서·앱별 연동 후보

- **일반 입력칸:** Windows UI Automation으로 대상·텍스트 범위를 읽고 선택할 수 있는지 확인한다. TextRange 자체에는 범용 텍스트 쓰기 기능이 없으므로, 부분 교체는 지원 패턴 또는 검증된 선택·붙여넣기 절차로 연결한다.
- **브라우저의 복잡한 편집기:** 범용 입력칸으로 처리할 수 없는 경우 확장 프로그램이나 편집기별 연동을 후속 검토한다. 원래 앱의 변경 이벤트와 실행 취소 기록까지 유지되는지 검증한다.
- **Word 직접 연동:** Range를 이용한 부분 교체를 후보로 둔다. 최소 범위만 수정하고 글자 서식·문단·표·필드·변경 추적을 별도로 확인한다. 텍스트를 쓸 수 있다는 사실만으로 모든 서식이 보존된다고 보지 않는다.
- **실제 한글 직접 연동:** 한컴 오토메이션을 후보로 검토하되 설치 버전과 선택 범위·문서 구조·Undo 동작을 먼저 실험한다. 공식 안내상 상업 목적 이용에는 별도 라이선스가 필요하므로, 이를 채택할 때 배포 형태와 이용 조건을 확인한다. 이는 일반적인 ‘한글처럼 하나씩 교정하는 UI’ 구현과는 별개의 결정이다.

## 8. 교정 엔진 및 품질

엔진은 교체 가능한 인터페이스로 구성한다. 첫 실험은 한글·영문을 처리하는 언어 모델과 로컬 규칙 조합을 후보로 두되, 모델·공급자·비용은 실제 문장 평가 뒤 정한다. 이 설계 단계에서는 API 호출이나 키 설정을 수행하지 않는다.

응답은 문장별 수정 후보와 이유를 구조화해 받고, 후보가 입력 문장과 대응하는지 검사한다. 입력 문서는 분석 대상 데이터로만 처리하며 문서 안의 지시를 실행하지 않는다. 숫자·날짜·금액·URL 보존 위반은 자동 선택 대상에서 제외하고, 의미 변경은 별도 평가 문장으로 확인한다. 보호 표현 검사는 의미 보존을 완전히 보장하지 않는다.

요청에는 초안 버전을 붙여 오래된 응답을 무시한다. 취소·실패·재시도 시 원문과 승인 결과를 유지한다. 클라우드 엔진 사용 시 실제 전송 대상과 범위를 알려주고, 문서 원문은 진단 로그에 기본 저장하지 않는다.

평가는 오탈자 검출뿐 아니라 정상 문장을 잘못 고치는 비율, 의미·어조 보존, 영어 및 혼용 처리, 응답 시간, 요청 비용으로 한다. 보존 검사 실패를 설명 없이 ‘교정 성공’으로 처리하지 않는다.

## 9. 구현 순서와 완료 기준

### A. 입력 연동 실험

선택 영역 읽기, 포커스 복귀, 원문 확인, 범위 교체를 짧은 일반 텍스트로 검증한다. 단순 편집기와 사용자가 자주 쓰는 앱을 포함해 초기 지원 범위를 정한다. 앱별로 읽기·선택·쓰기·서식·Undo 결과를 기록한다.

완료 기준: 선택 범위 밖의 글이 바뀌지 않고, 포커스 이동·원문 변경 시 잘못된 위치에 쓰지 않는다.

### B. 검토 화면과 변경 관리

준비한 예시 제안으로 세 가지 모드, 전후 비교, 하나씩 검토, 개별 선택·넘기기·되돌리기를 구현한다. 같은 단어 반복, 겹치는 제안, 줄바꿈, 한글과 이모지, 문장 길이 변화 사례를 확인한다.

완료 기준: 보기 전환이 같은 선택 상태를 유지하고, 적용 결과와 원문 복원이 일치하며, 오래된 제안을 적용할 수 없다.

### C. 실제 검사 및 선택 영역 반영

평가한 엔진을 연결하고, 검증된 일반 입력칸에서 확정한 초안을 선택 영역에 반영한다. 나머지 앱은 교정문 복사를 제공한다.

완료 기준: 원문 변경·취소·엔진 오류·반영 재시도에서 원문 손실과 중복 삽입이 없고, 반영 결과를 확인한다.

### D. 원래 문서에서 하나씩 교정

앱별 Adapter로 문제 위치 선택과 최소 범위 교체를 추가한다. 지원 앱과 문서 조건을 명시하고, 문서 서식·실행 취소를 함께 검증한다. 필요에 따라 Word·한글 연동을 추가한다.

완료 기준: 표·서식·문장 길이 변경·스크롤을 포함한 지원 조건에서 위치 이동, 부분 교체, 되돌리기가 검증된다.
